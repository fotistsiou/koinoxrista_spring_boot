# Domain Model

Reference for the business logic of the app: what each entity is, how they relate,
and why. Programming concepts live in [GLOSSARY.md](GLOSSARY.md).

Legend: ✅ built · ⏳ planned · ❓ open question

---

## The core idea

Every expense follows the same shape:

> A **Bill** (one expense) is split by a **SplitRule** among the participating
> **Apartments**, producing one **Debt** per apartment. Apartments settle their
> total balance with **Payments**.

```
Category 1 ──── N Bill N ──── 1 SplitRule (enum; set on Category, snapshot on Bill)
   │ N             │
   │               │ 1
   │               │
   │               N
   │             Debt N ──── 1 Apartment 1 ──── N Payment
   │                         N │     │ 1
   └───────────────────────────┘     │
                                     1
                                  AppUser
```

## Entities

### ✅ Apartment — table `apartment`
The fixed apartments of the building (Ισόγειο, 1ος, 2ος). Seeded on startup.

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| name | String | not null, unique |

### ✅ AppUser — table `app_user`
A login account: one per apartment. The admin is also a resident (the owner of an
apartment), so every user belongs to an apartment; the admin's extra access comes
from the role.

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| firstName, lastName | String | not null |
| email | String | not null, unique (the login username) |
| password | String | not null — will hold a BCrypt **hash**, never plain text |
| role | Role (enum) | not null, `@Enumerated(STRING)` |
| apartment | Apartment | `@OneToOne(optional = false)`, FK `apartment_id`, not null, unique |

The unique constraint on `app_user.apartment_id` is generated by Hibernate for the
`@OneToOne` join column: at most one user per apartment.

### ✅ Category — table `category`
Groups bills and decides **how** they are split and **among whom**. Seeded on
startup. An **entity, not an enum**, because the admin can add and edit categories
at runtime (see [Category rules](#category-rules)).

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| name | String | not null, unique |
| splitRule | SplitRule (enum) | not null, `@Enumerated(STRING)`, column `split_rule` |
| apartments | Set\<Apartment\> | `@ManyToMany`, join table `category_apartment` (`category_id`, `apartment_id`), `@OrderBy("id")` |

`apartments` = the apartments that share the bills of this category, loaded in id
order. Seeded:

| Category | SplitRule | Apartments |
|---|---|---|
| Κοινόχρηστο Ρεύμα | EQUAL_SPLIT | Ισόγειο, 1ος |
| Φυσικό Αέριο | METER_BASED | Ισόγειο, 1ος |
| Λέβητας – Βλάβες & Συντήρηση | EQUAL_SPLIT | Ισόγειο, 1ος |
| Απολύμανση | EQUAL_SPLIT | Ισόγειο, 1ος, 2ος |

### ✅ Bill — table `bill` (base class, `@Inheritance(JOINED)`)
One expense of one month. Holds the **data**; the SplitRule holds the **logic**.

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| amount | BigDecimal(10,2) | not null — may be negative (credit bill) |
| billDate | LocalDate | not null, column `bill_date` |
| category | Category | `@ManyToOne`, FK `category_id`, not null |
| splitRule | SplitRule (enum) | not null, `@Enumerated(STRING)`, column `split_rule` — **snapshot** of the category's rule |

`splitRule` is copied from the category by `BillService` at registration;
controllers never set it. Changing a category's rule later affects only future
bills — existing bills (and their debts) keep the rule they were calculated with.

Electricity, boiler faults/maintenance and disinfection bills are plain `Bill`s
(only `amount` needed). Boiler costs have their own category (Λέβητας – Βλάβες &
Συντήρηση); they are no longer plain bills of the gas category.

### ✅ GasBill extends Bill — table `gas_bill`
The monthly gas bill, which needs meter data. Shares the `id` with `bill`
(`gas_bill.id` is a FK to `bill.id`).

| Field | Type | Excel | Constraints |
|---|---|---|---|
| meterFloor | Integer | Μ1 — meter of the floor (1ος) | not null, column `meter_floor` |
| meterTotal | Integer | ΜΣ — total building meter | not null, column `meter_total` |
| consumptionCharge | BigDecimal(10,2) | Ω — consumption-based part | not null, column `consumption_charge` |
| meterApartment | Apartment | the apartment the floor meter belongs to (currently 1ος) | `@ManyToOne(optional = false)`, FK `meter_apartment_id`, not null |

**fixedCharge** (Excel: ΕΔΑ+ΔΕΣΦΑ, the fixed part) = `amount − consumptionCharge`.
Computed, **not stored**.

### ✅ Debt — table `debt`
What **one** apartment owes for **one** bill. Permanent record, never deleted.

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| amount | BigDecimal(10,2) | not null — may be negative |
| bill | Bill | `@ManyToOne`, FK `bill_id`, not null |
| apartment | Apartment | `@ManyToOne`, FK `apartment_id`, not null |

No paid/unpaid status.

### ✅ Payment — table `payment`
Money an apartment handed over, as a lump sum covering many debts.

| Field | Type | Constraints |
|---|---|---|
| id | Long | PK, IDENTITY |
| amount | BigDecimal(10,2) | not null |
| paymentDate | LocalDate | not null, column `payment_date` |
| apartment | Apartment | `@ManyToOne`, FK `apartment_id`, not null |

Linked to the **Apartment**, not to specific Debts.

## Relationships

| Relationship | Cardinality | Annotation (owning side) | FK lives in |
|---|---|---|---|
| AppUser → Apartment | 1 – 1 | `@OneToOne` on AppUser | `app_user.apartment_id` |
| Bill → Category | N – 1 | `@ManyToOne` on Bill | `bill.category_id` |
| Category → Apartment | N – N | `@ManyToMany` + `@JoinTable` on Category | `category_apartment` (`category_id`, `apartment_id`) |
| GasBill → Bill | inheritance | `@Inheritance(JOINED)` on Bill | `gas_bill.id` |
| GasBill → Apartment (meterApartment) | N – 1 | `@ManyToOne` on GasBill | `gas_bill.meter_apartment_id` |
| Debt → Bill | N – 1 | `@ManyToOne` on Debt | `debt.bill_id` |
| Debt → Apartment | N – 1 | `@ManyToOne` on Debt | `debt.apartment_id` |
| Payment → Apartment | N – 1 | `@ManyToOne` on Payment | `payment.apartment_id` |

All relationships are **unidirectional** for now (the "many" side knows the "one"
side, not the other way round; for Category ↔ Apartment, Category knows its
apartments, Apartment does not know its categories).

## Split rules

**EQUAL_SPLIT** — `amount / number of participating apartments`.
Electricity, boiler faults & maintenance (÷2); disinfection (÷3).

**METER_BASED** — monthly gas bill only:
- Ω = consumptionCharge (stored)
- fixedCharge = amount − consumptionCharge (computed)
- meterApartment = Ω × (meterFloor / meterTotal) + fixedCharge / 2
- the other participating apartment (Ισόγειο) = amount − meterApartment's share

## Bill registration and calculation

**Strategy** — one calculator per SplitRule, behind one interface:

```java
interface SplitCalculator {
    SplitRule supportedRule();
    Map<Apartment, BigDecimal> calculate(Bill bill, Set<Apartment> participants);
}
```

Implemented by `EqualSplitCalculator` and `MeterBasedSplitCalculator`
(`@Component`s in `service/split`). Calculators are **pure**: no repositories, no
Debt creation — they only return each apartment's share.

**`BillService.registerBill(bill)`**, `@Transactional`:
1. Reload the category by id (fails with "Category not found" if missing).
2. **Guard:** a `GasBill` in a category that is not `METER_BASED` is rejected —
   before anything is saved.
3. Copy the category's rule to the bill (`bill.splitRule` = snapshot).
4. Pick the calculator by `bill.splitRule`.
5. Save the bill.
6. Calculate the shares for the category's apartments.
7. Save one Debt per apartment.

A plain `Bill` in a `METER_BASED` category is rejected by the calculator ("requires
a GasBill") after the bill was saved — the transaction rolls back. Any failure
rolls back everything — there is never a bill without its debts.

## Category rules

- A `METER_BASED` category needs **exactly 2 apartments** — checked in
  `CategoryForm` (`@AssertTrue`) and again in `CategoryService.save`.
- Names are **unique** — checked in the controller (`existsByName` /
  `existsByNameAndIdNot` on edit), backed by the DB unique constraint.
- The rule **may be changed even when bills exist**: bills keep their snapshot,
  so only future bills use the new rule.

---

## Rounding rules

Shares must always **sum exactly** to the bill amount.

**EQUAL_SPLIT**
- share = amount ÷ n, rounded **DOWN** (toward zero) to 2 decimals.
- The leftover cents go one by one to the apartments in ascending id order
  (Ισόγειο first). E.g. 100.00 ÷ 3 → 33.34 / 33.33 / 33.33.
- Works for negative amounts too: −4.55 ÷ 2 → −2.28 / −2.27.

**METER_BASED**
- meter share = Ω × meterFloor ÷ meterTotal + fixedCharge ÷ 2, rounded
  **HALF_UP** to 2 decimals **once, at the end** (the intermediate division keeps
  10 decimals).
- The other apartment gets `amount − meter share`.
- Guards (each throws `IllegalArgumentException`): the bill must be a `GasBill`,
  there must be exactly 2 participants, and `meterApartment` must be one of them.

## Admin pages

| URL | Page | Result |
|---|---|---|
| `/admin/bills/new` | plain bill form: category, amount, date | `Bill` with `EQUAL_SPLIT` |
| `/admin/gas-bills/new` | monthly gas bill form: category, amount, Ω (`consumptionCharge`), `meterFloor`, `meterTotal`, meter apartment, date | `GasBill` with `METER_BASED` |
| `/admin/bills` | all bills, newest first, each with its debts per apartment | — |
| `/admin/apartments` | each apartment with total debts, total payments and balance, plus a "Πληρωμή" link per row | — |
| `/admin/payments/new` | payment form: apartment, amount, date | `Payment` |
| `/admin/categories` | all categories by name, with rule and apartments | — |
| `/admin/categories/new` | category form: name, rule, participating apartments | new `Category` |
| `/admin/categories/{id}/edit` | same form, prefilled | updated `Category` |

- **The category sets the SplitRule**; the bill forms never ask for it. The plain
  bill form lists only `EQUAL_SPLIT` categories, the gas form only `METER_BASED`
  ones, so the form type and the rule always match. `BillService` enforces the same
  rule again (see the guards above).
- The category forms redirect to `/admin/categories` after saving.
- After a successful registration each bill form redirects back to **itself** (empty
  form plus a success message), ready for the next bill. Validation errors and
  calculator errors re-show the form with the entered values.
- **Balances page** (`/admin/apartments`): balance > 0 = owes (χρωστάει),
  < 0 = credit / overpayment (πίστωση), 0 = settled (εξοφλημένο).
- **Payment form** (`/admin/payments/new`): the date is always prefilled with
  today. Opened from the balances page via `?apartmentId=…`, it is also prefilled
  with that apartment and, **only if the apartment owes**, with its current balance
  as the amount. After saving it redirects to `/admin/apartments` with a success
  message.

## Balance calculation

**balance = Σ(debts) − Σ(payments)** per apartment — never stored (principle 6).

- Computed **in the database** by `ApartmentRepository.findAllBalances`, with
  **one scalar subquery per sum** (one over `Debt`, one over `Payment`). Never one
  query that joins both debts and payments and then sums: every debt row would be
  repeated once per payment row (join fan-out), inflating both totals.
- `SUM` over no rows returns `NULL` (an apartment without debts or payments); the
  `ApartmentBalance` record turns it into `0`.
- `ApartmentBalance.balance()` = `totalDebts − totalPayments`.

## Payment rules

- **Amount must be positive** — a payment is money received. Refunds, if ever
  needed, are a separate concept, not a negative payment.
- **Date cannot be in the future.**
- **Overpayment needs no special handling** — it shows up as a negative balance
  (principle 5).
- **No PaymentService, on purpose:** registering a payment has no business logic,
  so `AdminPaymentController` saves through `PaymentRepository` directly (no
  pass-through services).

## Locked principles

1. **1 Bill → N Debts** — one debt per participating apartment.
2. **The rule lives on the Category; each bill keeps a snapshot of it.** History:
   the rule used to live on the Bill, because the gas category had two rules
   (METER_BASED for the monthly bill, EQUAL_SPLIT for boiler faults/maintenance).
   Moving boiler costs into their own category removed that reason. The snapshot
   keeps old bills correct when a category's rule changes.
3. **Logic (SplitRule) ≠ data (Bill)** — the rule is shared and stateless; monthly
   values live on the bill.
4. **Inheritance on Bill (JOINED)** — no nullable meter columns on non-gas bills.
5. **Overpayment (ρέστα) = negative balance**, not a separate field.
6. **No stored totals** — balance = Σ(debts) − Σ(payments). One source of truth.
7. **Negative amounts self-balance** — no special handling.
8. **Debt has no paid/unpaid status** — payments settle the balance in aggregate,
   not debt-by-debt.
9. **Payment links to Apartment, not to Debts** — the owner is paid a lump sum, so
   a payment is never allocated against specific debts.
10. **AppUser and Apartment stay separate entities** — an apartment is a physical
    unit that owns the financial history (debts, payments); a user is a person
    with credentials, and the occupant can change. Merging them would mix
    identity/security with finance (SRP) and hard-code the one-user-per-apartment
    assumption.
11. **Store the values entered from the source document, compute the derived
    ones** — e.g. GasBill stores `amount` and `consumptionCharge` (Ω) as printed on
    the gas bill and computes `fixedCharge`. Same idea as no stored totals: one
    source of truth, nothing to drift.

## Open questions

- ✅ ~~**Participants:** where do we store *which* apartments share an expense?~~
  **Resolved:** on the Category (`Category.apartments`, `@ManyToMany`). History is
  safe: Debts are computed once, when a bill is entered, and stored — so later
  changes to a category's apartments affect only future bills.
- ✅ ~~**Floor meter owner:** which apartment does the floor meter (`meterFloor`)
  belong to?~~ **Resolved:** stored on GasBill as `meterApartment`, next to
  `meterFloor` — never null, and each bill keeps its own value, so history stays
  correct. Not on Category (would be null for every non-gas category), not on
  Apartment (a gas concept on an unrelated entity), and never as a hard-coded
  apartment name in the service.
- ✅ ~~**Where the split logic lives:** methods on the `SplitRule` enum, or a
  calculation service that switches on the rule?~~ **Resolved:** Strategy pattern
  — one `SplitCalculator` per rule, chosen by `BillService` (see
  [Bill registration and calculation](#bill-registration-and-calculation)).
- ❓ **Export format** (Excel or PDF) — after the core works.
- ❓ **Editing / deleting a bill and its debts:** cascade from Bill to Debt, or an
  explicit delete of the debts in the service? Note the inconsistency: the Debt
  section says "permanent record, never deleted", which contradicts deleting a
  bill's debts. One of the two must give way when this is decided (e.g. "deleted
  only together with its bill").
- ✅ ~~**Gas form category:** choosing a non-gas category for a gas bill would
  still be calculated.~~ **Resolved:** categories carry a SplitRule; the bill-form
  dropdowns are filtered by rule, and the `BillService` guard rejects a `GasBill`
  in a non-`METER_BASED` category.
- ❓ **Bill PDFs:** store a OneDrive link, or upload the file?
- ❓ **Gas form input:** the admin enters `amount` and Ω (`consumptionCharge`) from
  the gas bill; form design not decided yet.
